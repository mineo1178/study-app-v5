# v1.82 学習セッションの競合対策

## 変更範囲

既存tasks documentに任意のsessionId、既存familyパスのdocumentにactiveStudyTaskIdを追加する。family documentが未作成なら部分作成する。collection追加・既存フィールド削除・migrationは行わない。旧タスクは開始時刻とタスクID等からlegacy IDを作り、最初の操作でsessionIdを保存する。START／再開ごとに新しいUUIDを生成し、一時停止ではIDを維持する。

## 書込み

- START：サーバーから既存タスクのdocument参照を取得し、transactionで全件を再読込する。同じtransactionでfamilyのactiveStudyTaskIdを読み書きする。再試行ではその参照先も再読込し、一覧取得後に追加された課題のSTARTとの競合を防ぐ。古いタイマーの停止と新しい開始を同時に確定する。開始時刻とタスクIDの既存優先順を維持。同じ課題への同時STARTは最初に確定した操作だけを受理する。
- PAUSE：sessionIdが一致する場合だけ保存。同じIDでも既に停止していれば変更しない。
- STOP／保存：sessionId照合と最新historyへの追加、タイマー終了を同一transactionで処理する。historyのidはsessionId。同じ履歴IDがあれば再送も別端末のSTOPも変更なし。別セッションなら拒否して現在のクラウド状態を表示する。
- 学習時間はクラウドのcurrentDurationと開始時刻から操作時刻までを算定する。10分未満無効、最大60分の活動P対象、reviewFlags等の既存条件は維持する。

## オフライン再送

新しいセッション操作はlocalStorageの順序付きキューへ、照合ID・操作ID・操作時刻を保持して保存する。通信失敗時は除去しない。確定後だけ操作ID単位で除去する。START→PAUSE→再開→保存を混合パッチにせず順に再送する。応答喪失後の再送は同じIDで冪等処理する。

v1.81以前の未送信タイマーパッチには照合情報がないため、自動再送しない。既存の旧キューは削除せず残し、同期状態をofflineとする。その場合は更新前後のローカル学習記録を確認する。通常のメモ・status更新は従来の部分更新を維持する。

## 再現方法

既存依存のみで実行する。Java 21以降とFirestore emulator JARが必要。JARは既存Firebase CLIキャッシュを使うか、FIRESTORE_EMULATOR_JARで指定する。新しいnpm依存の追加はない。

    npm test
    npm run test:emulator
    npm run build
    npx eslint src/game src/components/game src/study-utils.ts src/study-utils.test.ts src/study-session.ts src/study-session.test.ts tests/study-session.emulator.ts vitest.emulator.config.ts scripts/test-study-emulator.mjs
    git diff --check

emulator用runnerは127.0.0.1:8085でdemo-study-v182のみを使用する。本番設定・認証情報は読み込まない。使用中のポートなら既存サービスを停止せず失敗する。runnerが起動したJavaプロセスはテスト終了時に停止する。ログはOSの一時フォルダへ出力する。

既にemulatorが起動している場合は、FIRESTORE_EMULATOR_HOST=127.0.0.1:8085を設定し、npx vitest run --config vitest.emulator.config.tsで実行できる。localhost以外の接続先はテストが拒否する。

## emulatorで検証するケース

独立したFirebase App／Firestoreクライアント2つを使用する。

1. A START→B STARTでBのみactive。
2. A START→B STOPで履歴1件、Aにghost timerなし。
3. 新しいsessionへの古いSTOP／PAUSEを拒否。
4. 別課題の同時STARTで開始時刻が新しい方だけactive。
5. 同時STOPで既存historyを維持し追加は1件。
6. 保存済みSTOPの再送でも次のsessionを維持。
7. SDKのdisableNetworkで送信失敗を再現。B操作後にenableNetworkでキューを再送し、古い操作を拒否。
8. 同時刻STARTをタスクIDで一意に決定。
9. 同じ課題への同時STARTは1件だけ受理。
10. commit後の応答喪失を再現して再送し、履歴・活動P対象を二重計上しない。
11. 旧データのTimestamp形式の開始時刻やhistory／status省略をfallbackで扱う。
12. START中の別端末による課題作成でもactiveを1件に維持。
13. A START→B START→Aの遅延STOPでもBのsessionとfamily参照を維持し、Aの再送履歴を二重保存しない。新session開始後の古いRESUMEも拒否する。

## 制約・実機確認

対策はv1.82クライアントの操作に適用する。検証する2端末ともv1.82へ更新すること。旧バージョンのblind updateをサーバー側で拒否するFirestore rulesの変更・deployは今回行っていない。本番rulesがsessionIdおよびfamily documentの読取り・activeStudyTaskIdの部分書込みを許可することは実Firestoreで別途確認が必要。

STARTは既存タスク全件を読むため、タスク・履歴件数が増えると読取り量とtransactionの負荷も増える。共有collection内で開始対象のタスクdocumentが既に保存されている通常の操作を対象とする。

本番Firestoreの通信遅延、実スマホの画面OFF／OSによる終了はemulatorでは保証しない。実機では画面OFF・別アプリ・再読込で時間が継続すること、およびA START→B START／STOPで新しいタイマーだけが残り、履歴が1件になることを確認する。

参考：[Firestore transaction](https://firebase.google.com/docs/firestore/manage-data/transactions)、[emulatorと本番の差異](https://firebase.google.com/docs/emulator-suite/connect_firestore)。
